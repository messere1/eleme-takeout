# 店铺推荐算法说明

基准日期：2026-09-15。代码位置：`backend/src/main/java/cn/edu/tju/takeout/recommend/`。

本文描述「根据搜索历史与下单历史推荐店铺」的实现口径：用了哪些数据、如何打分、在哪里生效，以及当前的已知限制。

## 1. 目标与方案选型

顾客进入首页时，希望复购过的、符合口味的店铺排在前面。方案刻意选择**在线加权打分**，而不是协同过滤或离线训练模型：

- 数据量小（课程项目演示数据），在线计算足够快，不需要引入离线任务、特征存储和模型版本管理。
- 打分过程完全可解释，每条偏好都能追溯到具体的订单或搜索记录，便于验收和排查。
- 没有历史时能平滑退回全站热度，不存在「模型没训练好就没有结果」的冷启动空窗。

算法不使用任何机器学习模型，也没有离线任务和缓存，每次请求实时计算。

## 2. 流水线：召回 → 打分 → 重排

```
请求
 ↓
RecommendationService            编排顺序、装载数据
 ↓
① ShopRecallService   召回        多路召回 → 候选店铺 id
 ↓
② RecommendationScoring  打分     加权求和，降序
 ↓
③ RecommendationRerank   重排     打散、探索位
 ↓
返回
```

三段各自独立、各自可测：召回只决定「谁有机会被排序」，打分决定「谁更相关」，重排决定「这一屏合不合理」。调权重和调规则互不影响。

### 2.1 召回（`ShopRecallService`）

多路召回，任何一路命中都进候选：

| 通道 | 来源 | 对应的打分信号 |
| --- | --- | --- |
| A 历史下单店 | `orders` 里本人下过单的店铺 | 复购 |
| B 偏好品类下的店 | 顾客偏好品类 ∩ `shop_business_categories` | 品类 |
| C 搜索关键词命中的店 | 店名 / 经营范围 / 经营品类名 / 在售商品名命中搜索词 | 意图 |
| D 近期热门店 | 近 7 天订单量前 N | 热度（冷启动主来源） |
| E 按 id 兜底补齐 | 候选不足时补足条数 | 无（0 分） |

每一路都对应打分公式里的一个正信号，所以召回集合是**所有正分店铺的超集**——召回不会漏掉本该被推荐的店，只会多召回一些 0 分店（多一个 0 分候选无副作用）。

**退款通过的店在这里被剔除**，不再进入后续任何阶段。

热度和兜底两路直接在 SQL 里取前 N 条，不把全城店铺拉回内存再排。

### 2.2 打分（`RecommendationScoring`）

```text
score(s) = 3.0 · A_shop(s)                                          复购
         + 1.5 · Σ_{c ∈ 品类(s) ∩ 偏好品类} A_cat(c)                 品类
         + 1.0 · Σ_{k ∈ 偏好关键词} [∃p ∈ 在售商品(s): p.name⊇k]·A_kw(k)  意图
         + 0.3 · P(s)                                               热度（仅冷启动）
         + 0.8 · [品类(s) 命中当前餐段]                              时段
         - 2.0 · A_cancel(s)                                        负反馈
```

- `A` 是**带时间衰减的行为次数**：`A = 次数 × 0.5^(距今天数 / 14)`，半衰期 14 天。两周前的行为权重降到一半，一个月前降到约 1/4。
- `P` 是热度归一化值：近 7 天订单数 ÷ 当期最大值，取值 0~1。归一化是为了让热度只做微调，不压过取值范围在个位数的个人偏好。
- 关键词项是**每个关键词对每家店最多计一次**，不按命中条数累加。否则菜名里批量带某个词的店（40 个「炸鸡X」）光靠货架长度就能拿 40 分，压过一次满分复购的 3 分。
- 关键词的**匹配范围与 `ShopMapper.searchPage` 逐项一致**：店名、经营范围、经营品类名、在售商品名。搜索能搜到的店，召回和打分都认这个词。比对统一转小写，与搜索的 `ILIKE` 语义一致。
- 时段项一家店最多加一次，命中几个相关品类不叠加。
- 权重保持「复购 > 品类 > 意图 > 热度」的次序。负反馈权重 2.0 比单次复购（3.0）的一半略高，取消两次就足以压过一次复购。

同分按店铺 id 升序，保证结果稳定可复现。

### 2.3 重排（`RecommendationRerank`）

两条业务规则：

1. **同一经营品类最多连续 2 家**。两家店只要有一个共同经营品类就算同品类。
2. **每 2 家复购店之后插一家探索店**（约 70% 复购 / 30% 探索）。避免「点过一次川菜就天天推川菜」，也给没被历史覆盖的店留曝光位。

约束无法同时满足时（比如候选里全是同一个品类）退回分数优先，不会因为规则把店铺丢掉或重复。

## 3. 候选与过滤

只有同时满足以下条件的店铺参与推荐：

- `shops.status = 'OPEN'`
- 所属商家 `merchants.enabled = TRUE`
- **当前时间在 `opening_time`~`closing_time` 之内**（`Shop.isOpenAt`）。两个列可空，没配就当作不限时段；闭店时间小于开店时间按跨零点处理（如 17:00~02:00）；闭店端点不含，21:00 打烊的店 21:00 已不可下单。判定与下单链路的校验共用同一个方法，不会出现「推荐了却下不了单」。
- 不是本人退款通过的店

时段判断和 `status` 一样属于硬过滤：一家按营业时间已经打烊的店，复购信号再强也不推。

## 4. 时段上下文

同一个顾客早上和半夜打开首页，该看到的店完全不一样。

| 餐段 | 时段 |
| --- | --- |
| 早餐 | 05:00~10:00 |
| 午餐 | 10:00~14:00 |
| 下午茶 | 14:00~17:00 |
| 晚餐 | 17:00~21:00 |
| 夜宵 | 21:00~次日 05:00 |

经营品类到餐段的映射（`MealPeriod.BY_CATEGORY`）：

| 品类 | 适合的餐段 |
| --- | --- |
| 快餐便当 | 早餐、午餐、晚餐 |
| 奶茶饮品 | 早餐、下午茶、夜宵 |
| 小吃炸物 | 下午茶、夜宵 |
| 汉堡披萨 | 午餐、下午茶、晚餐、夜宵 |
| 日韩料理 | 午餐、晚餐 |
| 烧烤夜宵 | 晚餐、夜宵 |
| 甜品烘焙 | 下午茶、夜宵 |
| 健康轻食 | 早餐、午餐 |
| 中式快餐 | 早餐、午餐、晚餐 |
| 西式简餐 | 午餐、晚餐 |
| 奶茶甜品 | 下午茶、夜宵 |
| 地方菜系 | 午餐、晚餐 |

**顾客自建的品类不在表里，一律按中性处理**（不加分也不减分）。覆盖范围以库里实际存在的品类为准——当前是内置八个加上演示数据里的四个。新增品类时这张表要一并维护，否则新品类会静默拿不到时段加分。

## 5. 信号来源

| 信号 | 含义 | 数据来源 | 权重 |
| --- | --- | --- | --- |
| 店铺复购 | 顾客在该店下过单 | `orders` → `shop_id` | 3.0 |
| 品类偏好 | 顾客下单店铺的经营品类 | `orders` ⋈ `shop_business_categories` | 1.5 |
| 关键词偏好 | 搜索词命中店名 / 经营范围 / 品类名 / 在售商品名 | `user_search_history` + `shops` + `merchants` + `business_categories` + `products` | 1.0 |
| 全站热度 | 近 7 天各店订单量，归一到 0~1 | `orders` 按 `shop_id` 计数 | 0.3 |
| 餐段匹配 | 品类对得上当前餐段 | `shops` ⋈ `shop_business_categories` ⋈ `business_categories` | 0.8 |
| 取消扣分 | 顾客取消过的订单 | `orders.status = 'CANCELLED'` | −2.0 |
| 退款排除 | 顾客退款通过的订单 | `refund_requests.status = 'APPROVED'` | 直接排除 |

两个口径细节：

- **有效订单**指 `payment_status = 'PAID'` 且 `status <> 'CANCELLED'`。未支付、已取消的订单不产生复购和品类偏好，也不算热度。
- **关键词只取前 20 个**（按出现次数降序，`KEYWORD_LIMIT`），避免历史很长时把打分拖慢。

负反馈分两档处理，因为两种信号的可信度不同：取消常常和出餐慢、临时改主意、价格有关，不代表这家店不好，只扣分；退款通过意味着顾客已经为这家店拿回过钱，属于最强否定信号，直接排除。

**负反馈、时段都来自已有的表，不需要新增埋点。**

## 6. 生效位置

### 6.1 首页列表重排（`GET /api/v1/shops`）

登录顾客请求首页店铺列表时，先按原有规则分页，再把**这一页内**命中的店铺提到前面。

重排**只给当前页的店铺打分**，不扫全站。单店得分不依赖候选集（重排时热度项不参与），因此缩小候选集不改变页内相对顺序，却省掉了整站商品的全量扫描。首页是热路径，这一点对性能很关键。

- 只有 `score > 0` 的店铺才会拿到名次，没被任何偏好命中的店铺排在后面。
- 重排使用稳定排序，未被命中的店铺之间保持数据库返回的相对顺序，翻页时不会出现抖动。
- 分页元数据（`page` / `size` / `total` / `totalPages`）原样透传，重排只影响当页内部顺序。
- 游客（未带 Token 或 Token 无效）拿到的是未重排的原始顺序。

搜索接口 `GET /api/v1/shops/search` 不做重排——搜索是精确意图，按关键词返回原顺序更符合预期。

### 6.2 推荐位接口（`GET /api/v1/recommendations/shops`）

返回全站排序后的前 N 个店铺，默认 `limit=6`，允许范围 1~50（越界会被收敛到边界）。

**前 N 条是稳定前缀**：`limit=2` 的结果一定是 `limit=6` 结果的前两条。为此兜底召回池固定取 `MAX_LIMIT` 条，不随请求的 `limit` 变——否则池子大小跟着 `limit` 走，高分店可能只在 `limit` 较大时才进池，破坏前缀性质。

该接口**对游客开放**，未登录时退回全站热度，不会返回 401。

### 6.3 搜索历史的写入

`GET /api/v1/shops/search` 会在搜索成功后记录关键词，规则见 `SearchHistoryService`：

- 游客不记（`userId` 为空直接返回）。
- 空串和纯空白不记。
- 超过 50 字符截断到 50（`user_search_history.keyword` 是 `VARCHAR(50)`）。
- **只与紧邻的上一条去重**：搜索页从店铺详情返回时会重新搜一次，若不去重，同一个词会瞬间灌满历史。中间隔了别的词之后，同一个词会再记一次。
- **记录发生在搜索成功之后**：`shopService.searchShops` 会校验页码、每页条数和空关键词并抛 400，记在它前面的话，`page=0` 这类非法请求也会污染历史。

历史属于个人数据：顾客注销（`DELETE /api/v1/users/me`）时随账号一并删除。

## 7. 可调参数

| 常量 | 位置 | 值 | 含义 |
| --- | --- | --- | --- |
| `SHOP_WEIGHT` | `RecommendationScoring` | 3.0 | 复购店铺权重 |
| `CATEGORY_WEIGHT` | `RecommendationScoring` | 1.5 | 经营品类权重 |
| `KEYWORD_WEIGHT` | `RecommendationScoring` | 1.0 | 关键词命中权重 |
| `POPULARITY_WEIGHT` | `RecommendationScoring` | 0.3 | 热度兜底权重 |
| `TIME_FIT_WEIGHT` | `RecommendationScoring` | 0.8 | 餐段匹配权重 |
| `NEGATIVE_WEIGHT` | `RecommendationScoring` | 2.0 | 取消订单扣分权重 |
| `DECAY_HALF_LIFE_DAYS` | `RecommendationScoring` | 14.0 | 时间衰减半衰期 |
| `REPEAT_RUN` | `RecommendationRerank` | 2 | 连推几家复购店后插探索店 |
| `CATEGORY_RUN` | `RecommendationRerank` | 2 | 同一品类最多连续几家 |
| `POPULARITY_DAYS` | `RecommendationService` | 7 | 热度统计窗口 |
| `KEYWORD_LIMIT` | `RecommendationService` | 20 | 参与打分的关键词个数上限 |
| `MAX_LIMIT` | `RecommendationService` | 50 | 推荐接口返回条数上限 |

权重之间是相对关系，调参时保持「复购 > 品类 > 意图 > 热度」的次序即可。餐段映射表在 `MealPeriod.BY_CATEGORY`，新增内置品类时要一并维护。

## 9. 已知限制与后续改进

### 9.1 这一版做了什么

在初版（单一 `rank()` + 加权求和）基础上的改动：

| 改动 | 说明 |
| --- | --- |
| 拆成 召回 → 打分 → 重排 三段 | 三段各自可测，调权重和调规则互不影响 |
| 引入召回阶段 | 从「全站店铺打分」改为「多路召回后打分」，重排只给当页打分 |
| 负反馈 | 退款通过的店排除，取消过的店扣分；数据来自已有的 `orders` / `refund_requests` |
| 时段上下文 | 营业时间硬过滤 + 餐段匹配加权 |
| 重排打散 | 同品类最多连续 2 家；每 2 家复购店插 1 家探索店 |
| 关键词匹配范围对齐搜索 | 从只比商品名扩大到店名 / 经营范围 / 经营品类名 / 在售商品名 |
| 推荐位接入前端 | 首页新增「猜你喜欢」区块，调 `/recommendations/shops` |
| 前 N 条稳定前缀 | 兜底召回池固定 `MAX_LIMIT`，不随请求 `limit` 变 |
| 与上游 overnight 改动合并 | 删掉自写的 `ServingTime`，营业判定统一用 `Shop.isOpenAt`，与下单链路同口径；关键词召回补上「经营品类名」，与 `ShopMapper.searchPage` 逐项对齐 |

**行为的唯一有意变化**：召回成为打分的前置收敛。所有得分大于 0 的店铺之间，相对顺序与初版完全一致；变化只发生在「用来凑数的 0 分店铺」上。这一点由 `RecommendationServiceTest` 中初版的 12 条断言原样保留来保证。

**营业时间语义以 `Shop.isOpenAt` 为准**（起止相同视为打烊、闭店端点不含）。它与本模块早期自写版本有两处相反，合并时按「推荐与下单必须一致」的原则统一到了上游实现；`ShopOpenHoursTest` 补上了判定本身的边界覆盖。

### 9.2 仍待处理

#### 9.2.1 位置维度完全缺失

`shops` 只有 `shop_address` 字符串，没有经纬度，`users` 也只有 `address` 字符串。外卖的第一强约束「只在配送范围内」目前**无法实现**：距离衰减、地理热榜、配送范围过滤都做不了。

要补需要加 `shops.lat/lng`、用户收货点坐标，以及补演示数据。

#### 9.2.2 没有评分/口碑维度

schema 里没有 `rating`、`review`、`comment` 任何列或表，所以「店铺评分」「差评率」这类质量分算不出来。目前只能用订单量（热度项）近似「受欢迎程度」，但销量不等于口碑。

#### 9.2.3 偏好未做缓存

每次请求仍要读多张表算偏好和负反馈（`findShopAffinity` / `findCategoryAffinity` / `findTopKeywords` / `findNegativeAffinity` / `findRefundedShopIds`）。顾客偏好变化很慢，加个秒级 TTL 缓存即可。

#### 9.2.4 `MealPeriod` 的餐段映射是硬编码的

`BY_CATEGORY` 是一张写死在代码里的表，靠品类**名称**匹配。顾客自建的品类不在表里，按中性处理——这保证了不误伤，但也意味着自建品类永远拿不到餐段加分。当前表已覆盖库里实际存在的 12 个品类，但新增品类时必须手工补，漏了不会有任何报错（实测踩过一次）。

更彻底的做法是给 `business_categories` 加一列 `meal_periods`，让品类自带餐段。

#### 9.2.5 点击/加购物车还没有埋点

`cart_items` 只存当前购物车（`UNIQUE(user_id, product_id)`、无时间戳），不构成历史；前端也没有任何行为上报。曝光未点、加购物车未下单这类弱信号目前拿不到。想做需要前端埋点 + 新表。
