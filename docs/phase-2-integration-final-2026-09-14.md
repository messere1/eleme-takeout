## 缺陷与交接

### `DB-UPGRADE-001`：已有数据库卷无法直接升级

- 前置：用第一阶段 `schema.sql` 初始化一个独立数据卷，并插入标记用户。
- 操作：重启容器确认旧数据保留，再执行当前 `backend/src/main/resources/schema.sql`。
- 实际：`CREATE TABLE IF NOT EXISTS` 不会给旧表补新列；`users.avatar_url` 不存在。新代码读取该列会失败。Compose 初始化脚本也只在空卷首次初始化时执行。
- 期望：提供受版本管理的增量迁移，并在有旧数据的卷上验证字段、约束、序列及标记数据均完好。
- 责任建议：数据库/后端同学制定迁移与回滚方案；测试专员复测。不能用删除正式数据卷作为“修复”。

### `IO-FS-001`：磁盘写满后留下空图片文件

- 前置：独立测试数据库；上传目录为已填满的8KiB tmpfs。
- 操作：上传合法 PNG 作为用户头像。
- 实际：接口安全返回500并含 `traceId`，数据库头像仍为空，服务继续响应；但目录中新增一个0字节随机名 `.png` 文件。
- 期望：失败上传不留残余文件；再次上传或清理时不误用空文件。建议检查写入异常时的文件删除路径，再在隔离环境复测。
- 责任建议：图片上传实现同学修复；测试专员补回归和故障复测。

### `UI-ORDER-MOBILE-003`：有订单时顾客列表横向溢出

- 前置：最新 `2e211bc` 前后端连接独立 PostgreSQL 数据库，顾客已有至少1笔订单。空列表不能作为本用例的验收数据。
- 操作：以顾客身份打开 `/orders`，将真实 CSS 视口设为360、390、430、520及1280×720；检查 `document.documentElement.scrollWidth <= innerWidth`。
- 实际：Edge 130 的前四档滚动宽度均为526px，1280档通过；Firefox 137 在520档滚动宽度611px，1280档通过。页面没有脚本异常，问题是布局溢出。
- 预期：订单号、筛选控件、金额、操作按钮都保持在视口内，可换行或纵向排列，不产生页面级横向滚动。
- 初步定位：`frontend/src/views/Orders.vue` 的 `.orders-toolbar` 使用单行 flex，新增状态和起止时间筛选后没有窄屏换行规则；属于基于样式和测量的推断，修复前宜进一步检查具体溢出元素。
- 责任建议：前端同学调整窄屏布局；测试专员使用已加入“有订单”前置断言的浏览器矩阵回归，不用空列表冒充有数据页面通过。

上述故障均在一次性数据库、容器或 tmpfs 中复现；测试专用资源已清理，未删除或重建项目正在使用的 `takeout-postgres` 数据卷。当前真实开发服务没有被作为写入/故障注入对象。

## 可重复执行的测试入口

- `node scripts/read-only-perf.mjs 300 20`：只读性能脚本，默认请求本机8080；需要当前服务和店铺2001。
- `node scripts/full-flow.mjs`：仅允许本机18081独立后端，需设置 `TAKEOUT_FLOW_BASE` 与四角色密码环境变量；会写入订单/退款，**只能接一次性数据库**。
- 在 `frontend` 目录运行 `npx vite --config scripts/vite-integration.config.mjs`：仅供隔离测试，前端5174代理到后端18081，不覆盖用户的5173/8080服务。
- 在 `frontend` 目录运行 `node scripts/browser-matrix.mjs`：Playwright Edge/Chrome/Firefox 页面矩阵，需提供浏览器路径和四角色密码环境变量；有数据回归时设置 `TAKEOUT_EXPECT_ORDER_DATA=1`，否则没有订单的页面也可能得到假阳性。本轮仅 Edge 成功启动。
- 在 `frontend` 目录运行 `node scripts/firefox-matrix.mjs`：系统 Firefox/geckodriver 的520和1280视口矩阵；同样可设置 `TAKEOUT_EXPECT_ORDER_DATA=1`。

这些脚本不保存账号密码，也不改变业务实现。故障注入、旧卷升级和磁盘写满步骤必须继续在隔离环境执行，不得指向共享数据库。
